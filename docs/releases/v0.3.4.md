# ryzen-smu-cli v0.3.4

This compatibility release removes an unnecessary platform gate for Fire
Range and makes the signed positive Curve Optimizer read-back contract
explicit.

## Fire Range per-core operations

Fire Range (`Family 1Ah`, model `44h`, mobile package) uses the same
desktop-die per-core selector as Granite Ridge. Version 0.3.3 recognized its
CPU identity, topology summary, PM-table layout, and Vcore source, but then
rejected every per-core operation solely because the package was mobile.

Version 0.3.4 removes that package-only rejection. The general structural
safety checks still apply before any per-core query or write:

- the reported CCD count must be from 1 through 16;
- the physical slot count must equal eight slots per CCD;
- the enabled-core count must be nonzero and no larger than the slot count;
- the factory fuse map must contain an entry for every reported CCD; and
- enabled cores must still be mapped successfully through read-only Curve
  Optimizer queries.

Phoenix-family and heterogeneous Family 1Ah mobile processors remain
fail-closed. Their core layouts cannot safely be represented by simply
removing the same gate.

## Positive factory Curve Optimizer offsets

The CLI continues to preserve signed Curve Optimizer values from hardware.
`--get-offsets-terse` may therefore include positive values such as `10` when
a system ships with a factory per-core offset of `+10`. Consumers must not
apply a negative-only algorithm limit while parsing hardware read-back values.
The write interface remains bounded to `-50` through `50`, with firmware as
the final authority.

## Validation

The automated Release suite covers the Fire Range platform gate, preserves
the existing fail-closed mobile families, and verifies the exact terse output
for a positive `+10` hardware offset. Before a public release, the read-only
hardware smoke test should be run on a Fire Range system, with particular
attention to `--get-offsets-terse`, `--get-physical-cores`, and
`--get-enabled-cores`.
