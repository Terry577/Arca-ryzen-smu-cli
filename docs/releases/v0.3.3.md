# ryzen-smu-cli v0.3.3

This maintenance and compatibility release corrects the initial Vcore
mapping and expands the SMU-native voltage investigation path across known
Zen 4 and Zen 5 client silicon. It explicitly distinguishes hardware-verified
layouts from structural candidates rather than treating every product name as
equally qualified.

## Highlights

- Granite Ridge now reads live VDDCR CPU telemetry at PM-table entry 49. The
  previous entry 18 was a peak/limit-style value and could overstate Vcore.
- Raphael, including table `0x00540104`, reads live VDDCR at entry 47.
- Dragon Range table `0x00540208` uses its shifted live VDDCR entry 48.
- Phoenix, Phoenix 2, Hawk Point, Strix Point, Krackan Point, and Strix Halo
  use silicon-specific SMU SVI rail candidates instead of guessing an APU PM
  table field.
- Fire Range is recognized separately from Granite Ridge by its mobile package
  class. Its exact matching PM-table layouts remain structural candidates
  until synchronized Fire Range hardware captures qualify them.
- PM-table layouts are now guarded by exact version and structure size.
- `--info` identifies each selected source as verified or structural.
- `--info` now includes stable `Logical` and `SMT` rows sourced from CPUID
  topology. On fail-closed mobile/APU platforms, its physical-core count uses
  the CPUID-derived count rather than an unqualified fuse-slot map.
- `--diagnose-vcore` captures the selected reading and raw SVI candidates as a
  read-only JSON report for qualifying new CPUs and firmware.

Selection is based on CPUID family/model/package class and exact telemetry
metadata, not on the marketing name. OEM, regional, X3D, and disabled-iGPU
SKUs using the same silicon therefore share a selector without maintaining a
fragile product-name list. This does not turn a known marketing family into a
promise that every future BIOS PM-table revision is already mapped.

Structural mappings are available as experimental sources in this release so
real-hardware captures can be collected. They are not hardware-verified until
their voltage tracks synchronized motherboard telemetry.

## Collecting a Vcore diagnostic

Run the diagnostic from an elevated PowerShell. It performs register and
telemetry reads only:

```powershell
.\ryzen-smu-cli.exe --diagnose-vcore --samples 40 --interval-ms 150 `
  > .\vcore-diagnostic.json
```

`--samples` accepts 1 through 1000 and defaults to 40. `--interval-ms` accepts
50 through 60000 milliseconds and defaults to 150; it is shared by
`--diagnose-vcore` and `--stream-vcore`. The JSON includes a typed source and
confidence, family/model/package, motherboard, BIOS, firmware and SMU/PM-table
metadata, physical/logical core counts, threads per core and SMT state,
topology qualification and reason, selection state, selected
readings, raw candidate registers, requested/captured/cancelled sample state,
producing CLI version, and selected/register success and failure counts. On
unmapped firmware the
report preserves the unsupported reason and raw evidence instead of selecting
a speculative voltage.

## Diagnostic read policy

The diagnostic uses the official signed PawnIO `AMDFamily17` read-only SMN
channel, including the Family 1Ah `0x000730xx` range. Each sample reads every
candidate in its fixed platform whitelist under one PCI-bus lock; it does not
scan arbitrary SMN addresses.

| Diagnostic platform selector | Fixed raw-register groups |
| --- | --- |
| Family `19h`, models `74h`, `75h`, `78h`, `7Ch` | Legacy `0x0005A008` … `0x0005A014` plus extended `0x0006F034` … `0x0006F03C` |
| Family `1Ah`, models `20h`, `24h`, `60h`, `68h` | Legacy `0x0005A008` … `0x0005A014` plus extended `0x0006F034` … `0x0006F03C` |
| Family `1Ah`, model `70h`, or model `44h` mobile package | Extended `0x0006F034` … `0x0006F03C` plus Family 1Ah `0x0007300C` … `0x00073014` |
| Every other family/model/package | No speculative raw SMN candidates |

Every raw register has a typed name and role. VID-to-volts decoding is applied
only to `core-plane` candidates. `status`, `unknown`, and other-plane registers
remain typed raw evidence and are not presented as voltage candidates; named
status flags or raw hardware-VID bit fields may still be retained without
converting them to Vcore.

## Safety behavior

The program refuses unknown family/model combinations, unknown PM-table
versions, known versions with an unexpected size, unavailable SVI planes,
sentinel register values, invalid VID encodings, truncated tables, and
implausible voltage values. Normal Vcore reads fail closed; they never select
a nearby table layout or substitute per-core VID for the CPU supply rail.

Phoenix-family package identity and structural Vcore diagnostics remain
available, but per-core fuse mapping on Family `19h` models `74h`, `75h`,
`78h`, and `7Ch` is not yet hardware-qualified. The same fail-closed policy
applies to heterogeneous Family 1Ah models `20h`, `24h`, `60h`, `68h`, and
`70h`, and to Fire Range (`1Ah/44h` mobile package). Commands requiring a
trusted per-core map refuse those operations until real hardware evidence is
available.

Use `--info` and the JSON from `--diagnose-vcore` when reporting hardware that
remains unsupported. Include the CPU name/CPUID, motherboard and BIOS, SMU
version, PM-table version and size, and Vcore telemetry-source line.
